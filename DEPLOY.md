# Deploying and running TrustVault

Two ways: on your own machine (for development and running the tests), and on Render (the live URL for the judges).

---

## A. Run on your own machine (from a clean clone)

### 1. Install

- **Node.js 20 or newer** (22 recommended): https://nodejs.org
- **PostgreSQL 14 or newer**: https://www.postgresql.org/download/
- **Git**

### 2. Create the databases (one time)

```bash
psql -U postgres -f server/db/create-local-db.sql
```

This creates a user `trustvault` (password `trustvault_local`, local only) and two databases: `trustvault_dev` for the app, and `trustvault_test` for the tests. The tests wipe `trustvault_test` every run, so never point them at real data.

### 3. Install, set up, build, start

```bash
git clone <repo-url> trustvault
cd trustvault
cp .env.example .env          # Windows: copy .env.example .env
npm install
npm run setup                 # creates tables, then seeds demo accounts and documents
npm run build                 # builds the React app into client/dist
npm start                     # open http://localhost:3000
```

Sign in with the accounts listed in the README.

### 4. Run the tests

```bash
npm test                      # 151 tests against trustvault_test
npm run test:authz-removal    # removes each of the 34 permission checks in turn; all must be caught (~5 min)
npm run verify-audit          # checks the audit hash chain in the dev database
```

### Development mode (live reload)

```bash
npm run dev                   # API on http://localhost:3000, restarts on changes
npm --prefix client run dev   # React on http://localhost:5173 (calls the API through a proxy)
```

## B. Deploy to Render (live URL)

`render.yaml` describes the whole setup: one Node web service and one PostgreSQL database.

1. Push the repository to GitHub (public, as the brief requires).
2. On https://render.com sign in with GitHub, then **New > Blueprint** and pick the repository.
3. Render reads `render.yaml`. Nothing needs typing: `AUDIT_HMAC_KEY` is generated by Render, and the demo account passwords are set in `render.yaml` (they are public on purpose, matching the README, and only unlock demo data). Give the Blueprint a name, for example `trustvault`.
4. Click **Apply**. The first build takes a few minutes. When the service shows **Live**, open its `https://trustvault-xxxx.onrender.com` URL and sign in.
5. Put that URL in the README under "Live demo".

### What happens on each deploy

- Build: `npm ci && npm run build` (installs the server, then builds the React app).
- Start: `npm run migrate && npm run seed && npm start`. The schema is idempotent and the seed only runs when there are no users, so redeploys never duplicate or overwrite data.

### Things to know about the free plan

- The service sleeps after 15 minutes without traffic; the first request then takes about 30–60 seconds. Open the site once before a demo or judging session.
- Render's free PostgreSQL expires after 30 days. That is enough for judging; upgrade or redeploy after that.
- **Do not change `AUDIT_HMAC_KEY`** after the first deploy. Every existing audit entry is sealed with it; a new key makes the chain check fail.
- The `[audit-anchor]` lines in Render's **Logs** tab are the hash of each new audit entry, kept outside the database. They let you prove the newest entries were not deleted (see THREATS.md, T19).

### Optional hardening on a paid database

Create a second database role for the app with no `UPDATE` or `DELETE` rights on `audit_log`, and keep the owner role only for migrations. On the free plan we rely on the triggers plus the keyed hash chain instead (see THREATS.md).

## Resetting the demo data

Locally:

```bash
psql -U trustvault -h localhost trustvault_dev -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"
npm run setup
```

On Render, the same command can be run from the database's **Connect > PSQL** command. This deletes everything, including the audit log, so only do it before judging starts.
